Goal: Move LandLinq's existing auto-YOC underwriting engine (calculateYOCForProductTypes and calculateYOCBreakdown, currently in client/src/pages/analyst-dashboard.tsx starting around line 1741) from client-side to a shared server service, and let each developer group override the national PRODUCT_TYPE_YOC_PRESETS with their own assumptions, entered through a settings form. Do not simplify or drop any of the existing modeling logic (vacancy/LTL/concessions/bad debt, management fee, coastal insurance tiers, state-level rent/land multipliers, NC sub-market overrides, HelloData comp-based rent for conventional/BTR, the "BEST" multi-type comparison) — this needs to stay exactly as thorough as it is today, just parameterizable per developer.

Schema — extend the existing developerProductTypes table (shared/schema.ts, already has developerProfileId, name, minAcres, maxAcres, minRentPsf, minRentPerUnit) with new nullable columns matching the shape of PRODUCT_TYPE_YOC_PRESETS: dua, hardCostPu, assumedLandCostPu, assumedLandCostPuCoastal, softCostPct, otherIncomePum, fixedOpExPu, insurancePuNc, insurancePuCoastal, vacancyPct (default 0.05), ltlPct (default 0.01), concessionPct (default 0.01), badDebtPct (default 0), mgmtFeePct (default 0.0275), and unitMix (jsonb, array of {pct, avgSF, monthlyRent}). All nullable — a developer with none of these set falls back to the existing global preset unchanged.
Server — extract the calculation into server/services/yocUnderwritingService.ts. Port calculateYOCForProductTypes and calculateYOCBreakdown from analyst-dashboard.tsx into this file nearly verbatim (same math, same coastal/state-multiplier logic, same comp-based rent logic), but change the preset lookup: instead of always reading from the hardcoded PRODUCT_TYPE_YOC_PRESETS object, first check whether the deal's developerProfileId has a matching row in developerProductTypes with underwriting fields populated (non-null hardCostPu) for that product type name; if so, build the preset object from those fields instead of the hardcoded table. Keep the hardcoded PRODUCT_TYPE_YOC_PRESETS object as the fallback default — don't remove it.
Auto-recompute on change, server-side. Add a call to this service (updating deals.automatedYoc and the underlying NOI/TDC fields, same as today) triggered whenever: (a) a deal is created or its productTypes, unitCount, sizeAcres, or askingPrice changes, and (b) whenever a developer's developerProductTypes underwriting fields are updated — in that second case, recompute automatedYoc for every existing deal tied to that developer profile with a matching product type, not just new deals. Respect the existing yocOverrides per-deal manual override — if an analyst has manually overridden a field for a specific deal, that override still wins over the auto-calculated value, exactly as it does today.
Settings UI (in-app form, not a spreadsheet upload) — add an "Underwriting Assumptions" section to client/src/pages/developer-criteria-settings.tsx, near the existing product-type criteria fields, using the same rounded-2xl/bg-white card styling as the rest of that page. For each of the developer's product types, a form with labeled numeric fields for every column added in step 1 (Hard Cost/Unit, Land Cost/Unit non-coastal and coastal, Soft Cost %, Other Income/Unit/Month, Fixed OpEx/Unit, Insurance/Unit non-coastal and coastal, Vacancy %, Units/Acre, and a small repeatable unit-mix table for % of units / avg SF / monthly rent). Leaving a field blank means "use the national default for this field" — don't force a developer to fill in every single number if they only want to override, say, hard costs.
Client cleanup — replace the client-side calculation in analyst-dashboard.tsx with a read of the server-computed deal.automatedYoc (which it already reads today) — remove the now-redundant calculateYOCForProductTypes/calculateYOCBreakdown functions from the client file once the server service is confirmed working, so there's one source of truth instead of two copies of the same logic.

Test with at least one deal that has a developer with custom assumptions set, and one deal whose developer has none set (should still produce the exact same result as today's global-preset calculation) — regression-checking the no-override case is the important part, since that's every existing deal today.

server/services/yocUnderwritingService.ts's recomputeDealYoc (~lines 874-889) picks a developer profile to source underwriting overrides from when none is explicitly passed: it calls getDeveloperProfileIdsForDeal(dealId), which queries partnerDeveloperSends with no ORDER BY, and takes the first result — meaning it's non-deterministic which company's custom assumptions get used.

The problem: deals.automatedYoc/automatedIrr/projectedNOI (and related fields) are single columns on the shared deals row, not per-developer. When a deal has been sent to two Investment Companies with different custom developerProductTypes presets (their own hard cost, land cost, rent assumptions), every routine background update to that deal (server/storage.ts:1436 on creation, server/storage.ts:1811 in updateDeal — triggered by geocoding, MSA re-matching, QCT changes, etc., all called with no profileId from server/unifiedDealPipeline.ts) re-triggers this recompute and can silently overwrite the deal's YOC/IRR figures with whichever company's private underwriting assumptions happened to be picked — and that number is then visible to every company that deal was shared with.

This needs a real design decision, not just a query tweak: either (a) YOC/IRR should be computed and stored per-developer-per-deal (a join table keyed by dealId + developerProfileId) instead of as single columns on the shared deal, so each company only ever sees figures computed from their own assumptions, or (b) if a single shared "baseline" figure is intentional (e.g. computed from platform-default assumptions, not any one company's custom overrides), recomputeDealYoc should never use a specific developer's overrides when called without an explicit profileId — it should use the platform default preset instead, and callers that legitimately want a specific company's view (e.g. that company's own deal detail page) should pass developerProfileId explicitly.

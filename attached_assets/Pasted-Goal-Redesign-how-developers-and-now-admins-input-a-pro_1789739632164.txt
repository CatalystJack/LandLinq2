Goal: Redesign how developers (and now admins) input a product type's Auto-YOC underwriting assumptions. Right now these 14 fields live in one flat, unlabeled grid inside client/src/pages/developer-criteria-settings.tsx's product type editor, mixed in with the basic acreage/rent criteria, with a raw JSON textarea for unit mix. Pull this into a dedicated, reusable panel with better structure, and add the exact same capability to the admin side so Apex/LandLinq staff can set these during onboarding, before the investment company ever logs in.

Do NOT change any calculation logic, the schema, or the existing admin/developer PATCH endpoints' validation (server/routes.ts underwritingNumericFields / underwritingPercentFields / parseProductTypeUnderwriting / parseAdminProductTypes) — this is a frontend-only redesign that must keep sending the exact same field shape those functions already accept (numeric strings for the 14 fields, and unitMix as an array of {pct, avgSF, monthlyRent} objects, not a JSON string).

1. New shared component client/src/components/yoc-assumptions-panel.tsx, props: { productType, nationalDefaults, value, onChange }. Group the 14 fields into four labeled subsections: "Development Costs" (density, hardCostPu, assumedLandCostPu, assumedLandCostPuCoastal, softCostPct), "Operating Income & Expenses" (otherIncomePum, fixedOpExPu, insurancePuNc, insurancePuCoastal, mgmtFeePct), "Rental Loss Assumptions" (vacancyPct, ltlPct, concessionPct, badDebtPct), "Unit Mix".
   - When a field is blank, show its national default as greyed placeholder text inside the input, so blank = a visible number, not a guess.
   - For the percent fields, change the input to accept a whole-number percent with a trailing "%" suffix, converting to/from the stored decimal at the boundary — still send a decimal string to the API.
   - Replace the unit-mix JSON Textarea with a repeatable-row table (% of units / Avg SF / Monthly rent, delete icon per row, "Add row" button below) matching the existing "Add product type" pattern. Validate rows client-side (pct 0-100%, avgSF > 0, monthlyRent >= 0) with inline errors. Emit/store the array of {pct, avgSF, monthlyRent} objects directly — never build or parse a JSON string.
   - Add a "Reset to national defaults" button per subsection.
   - Add a "Copy from another product type" control at the top (shown only when more than one product type exists) that copies all 14 fields + unitMix from another product type into this one.

2. In client/src/pages/developer-criteria-settings.tsx: remove the current inline 14-field grid + unit-mix Textarea from the product type editor block. Replace it with a single "Underwriting assumptions" button/link on each product type row that opens the new YocAssumptionsPanel (inline expandable section or Dialog/Sheet — match whichever pattern this page already uses elsewhere). The product type row itself goes back to just Product type / Min acres / Max acres / Min rent $/SF.

3. In client/src/pages/admin-investment-companies.tsx: add the identical "Underwriting assumptions" button to each product type row in the admin's product type editor (~line 300-350), opening the same shared YocAssumptionsPanel, wired to the same 14 fields on that product type object. Save through the existing admin PATCH endpoint (/api/admin/investment-companies/:profileId) exactly as the other product type fields already do — no new endpoint needed, since parseAdminProductTypes already accepts these fields.

Non-regression: don't touch yocUnderwritingService.ts, the calculation logic, the schema, or the PATCH/POST endpoint validation functions. Don't change how developer-role users' product type basic fields (name/acres/rent) save. This is purely a UI reorganization plus extending the same capability to the admin page.
